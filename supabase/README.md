As migrations criam o PostgreSQL usado pelo backend Express. O login continua na tabela `usuarios`, com os hashes atuais e `JWT_SECRET`; elas não criam usuários no Supabase Auth.

Execute em ordem os arquivos de `migrations/` usando uma conexão administrativa de um projeto dedicado. Os arquivos são estruturais e não inserem dados. Para migrar uma instalação existente, importe o SQLite antes de iniciar o backend. O arquivo `seed.sql` é opcional e exclusivo para instalação nova; não o aplique antes da importação.

Aplique as duas migrations antes de iniciar a aplicação. A primeira já habilita RLS; a segunda remove os privilégios automáticos da Data API, inclusive de `service_role`. Em uma instalação nova, o seed cria apenas empresa, Matriz, local de estoque, papéis e categorias. O primeiro administrador deve ser criado pelo comando de bootstrap do backend, sem senha padrão no SQL.

O contrato em `schema-contract.json` descreve as 38 tabelas em ordem de dependência, suas 431 colunas, os campos de identidade e as chaves estrangeiras. Os nomes foram mantidos. Valores financeiros e quantidades usam `numeric`; IDs usam `bigint generated by default as identity`, permitindo importar os IDs originais. Datas e horas, XML e JSON permanecem em `text`, e indicadores permanecem em `integer` com valores 0/1, preservando a representação consumida pela aplicação. As datas padrão são produzidas em UTC. Não foi criado um trigger de atualização automática: o backend mantém os mesmos momentos de atualização do SQLite.

As chaves estrangeiras são diferíveis até o fim da transação de importação. As restrições únicas e os índices parciais permanecem imediatos para suportar `ON CONFLICT` e impedir mais de um caixa aberto por usuário. O contrato inclui `vendas.cliente_id`, que era acrescentado sob demanda no SQLite, e o relacionamento com `clientes`. O importador deve conferir integridade e ajustar as sequências ao maior ID importado.

RLS está habilitado em todas as tabelas da aplicação. Não existem políticas para acesso pelo navegador. As permissões de tabelas e sequências foram revogadas de `PUBLIC`, `anon`, `authenticated` e `service_role`. Isso inclui as permissões automáticas que alguns projetos Supabase atribuem a tabelas novas. `DATABASE_URL` deve existir somente no backend e usar uma conexão confiável com o proprietário das tabelas ou uma função de servidor revisada com `BYPASSRLS`. A API continua verificando papéis, mercados autorizados e `X-Loja-Id` em todas as operações.

Uma chave publicável ou `anon` não substitui `DATABASE_URL`. Não envie a conexão do banco ou uma chave privilegiada para variáveis `VITE_*`. Como a aplicação usa conexão direta, a Data API do projeto pode permanecer desativada. O `config.toml` desativa a Data API local e a execução automática do seed; ele não altera a configuração da API de um projeto remoto, que deve ser revisada no painel do Supabase. Migrations futuras devem habilitar RLS e revisar privilégios explicitamente; privilégios padrão valem para o papel que cria os objetos.

O teste SQL em `tests/backend_only.sql` verifica catálogo, RLS e permissões usando somente recursos nativos do PostgreSQL. Ele pode ser executado em um PostgreSQL local descartável com papéis de teste `anon`, `authenticated` e `service_role`; não depende de `auth.uid()` ou pgTAP.
